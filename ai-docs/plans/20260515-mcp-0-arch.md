# bodhi-pi MCP Integration — Architecture Map

**Date:** 2026-05-15  
**Status:** EXPLORATION (read-only, no edits yet)

This document maps the bodhi-pi monorepo structure to support MCP integration planning. It covers package layout, ACP extension mechanics, KV storage, slash commands, provider patterns, e2e testing strategy, and the session lifecycle hooks where MCPs would hydrate.

---

## 1. Package Layout

All packages live under `packages/`. The core agent is `bodhi-pi` (embeddable, host-mediated, ACP-speaking). Four reference hosts prove feature parity across Node, browser, and split deployments.

### Core Package
**`@bodhiapp/bodhi-pi`** (publishable)  
- **Role:** Embeddable agent. Host-injected Filesystem, SessionStore, ScriptExecutor, Terminal, KvStore.
- **Entry:** `/packages/bodhi-pi/src/index.ts` — exports `createBodhiPiAgent`, `BodhiPiClient`, event types, settings types.
- **Main factory:** `createBodhiPiAgent(config: BodhiPiConfig)` in `src/acp/agent.ts`
  - Requires: `sessionStore`, `filesystem`, `getApiKey` (optional)
  - Optional: `eventHandlers`, `extensionFactories`, `kvStore`, `homeDir`, `globalFilesystem`, `scriptExecutor`, `terminal`, `models`, `compaction`, `defaultThinkingLevel`
  - Returns: `BodhiPiAcpAgent` (implements ACP `Agent` interface)

### Adapter Packages (Publishable)
**`@bodhiapp/bodhi-pi-node`**  
- Exports: `createNodeFilesystem({rootCwd})`, `createSqliteSessionStore({dbPath})`, `createNodeScriptExecutor()`, `createNodeTerminal()`.

**`@bodhiapp/bodhi-pi-browser`**  
- Exports: `createZenfsFilesystem()`, `createDexieSessionStore()`, `createBrowserScriptExecutor()`, `createMessagePortStream()`.

### Reference Hosts (Workspace Packages, Private)
| Host | Transport | Status | Notes |
|---|---|---|---|
| `bodhi-pi-cli` | ACP JSON-RPC over stdio (in-process pair) | Private PoC | Node REPL; hand-rolled commands; real FS + SQLite |
| `bodhi-pi-web` | ACP JSON-RPC over Web Worker MessagePort | Private PoC | React/Vite; browser-only; ZenFS + Dexie |
| `bodhi-pi-ws-server` + `bodhi-pi-ws-frontend` | ACP JSON-RPC over WebSocket | Private PoC pair | Node WS server (multi-tenant SQLite); thin React frontend |
| `bodhi-pi-http` | ACP JSON-RPC over HTTP+SSE (per-turn agent rebuild) | Private PoC | Single Node project; per-request fresh agent hydration |

### Test Infrastructure
**`bodhi-pi/test-apps/`** — four deployable app stubs (built alongside e2e)
- `in-memory/` — in-process ACP pair, memory FS/sessions
- `cli/` — Node stdio harness
- `http/` — HTTP server harness
- `browser/` — browser worker harness
- `chrome-ext/` — Chrome extension harness
- `app-utils/` — shared: just-bash terminal adapter, just-bash-fs adapter

## 2. ACP Extension Mechanism

bodhi-pi deviates from upstream ACP: **`fs/*` and `terminal/*` methods are absent** because the agent owns those. Custom methods live under `_bodhi-pi/<area>/<verb>`, advertised via `agentCapabilities._meta["bodhi-pi"]`.

### Extension Registry & Dispatcher

**`src/extensions/runner.ts`** — `ExtensionRunner` class  
Aggregates contributions from extension factories. Builds a per-extension API and runs each factory through `ExtensionRunner.build(...)`.

```typescript
// From src/extensions/runner.ts:79-104
static async build(opts: {
  conn: AgentSideConnection;
  sessionStore: SessionStore;
  extensions: RegisteredExtension[];
  requestSlashableRefresh?: RequestSlashableRefresh;
  logger?: RunnerLogger;
}): Promise<ExtensionRunner> {
  const runner = new ExtensionRunner({ conn: opts.conn, sessionStore: opts.sessionStore, ... });
  for (const ext of opts.extensions) {
    const api = runner.buildApiFor(ext.name);
    try {
      await ext.factory(api);  // ← Extension runs, registers contributions via api
    } catch (err) {
      runner.errors.push({ extensionName: ext.name, error: err });
      runner.logger.error(`[bodhi-pi extension:${ext.name}] factory threw`, err);
    }
  }
  return runner;
}
```

**Per-extension API surface** (`src/extensions/types.ts` `ExtensionAPI`):
```typescript
export interface ExtensionAPI {
  on<T extends BodhiPiEventType>(type: T, handler: ExtensionEventHandler<T>): () => void;
  registerTool<P extends TSchema, D = unknown>(def: ExtensionToolDefinition<P, D>): () => void;
  registerCommand(name: string, def: ExtensionCommandDefinition): () => void;
  registerProvider(name: string, config: ProviderConfig): () => void;
  events: ExtensionEventBus;  // Inter-extension pub/sub
  appendEntry(sessionId: string, entry: ExtensionEntryPayload): Promise<void>;
  sendMessage(sessionId: string, content: TextContent | TextContent[] | string): Promise<void>;
  requestSlashableRefresh(sessionId: string): Promise<void>;
}
```

**Collision semantics:**
- **Tools:** Builtin tools win; extensions cannot shadow `read`, `write`, etc.
- **Commands:** Project-defined commands beat extension-registered commands (user intent wins).
- **Providers:** First registered wins.

### Extension Event Handlers

**`src/events/dispatcher.ts`** — `EventDispatcher` class  
Sequential async dispatcher. Errors caught and logged; peer handlers still run. Five mutation-aware emitters merge handler return values.

```typescript
// Mutation-aware emitters (src/events/dispatcher.ts:75-130)
async emitInput(event: InputEvent): Promise<{ text: string; handled: boolean }>

async emitToolCall(event: ToolCallEvent): Promise<{ block: boolean; reason?: string }>
async emitToolResult(event: ToolResultEvent): Promise<ToolResultEventResult>
```

**Event types:** `src/events/types.ts`
- Session lifecycle: `session_start`, `session_shutdown`
- Agent run: `agent_start`, `agent_end`, `turn_start`, `turn_end`
- Mutable hooks: `input`, `before_agent_start`, `before_provider_request`, `tool_call`, `tool_result`
- Streaming: `message_start`, `message_update`, `message_end`
- Tool execution: `tool_execution_start`, `tool_execution_end`
- Observations: `tool_call`, `tool_result`, `message_chunk_update`, `auth_change`, `model_select`, `settings_change`, compaction, fork, branch-summary, etc.

### How Client/Host Route Extension Methods

**Client side** (`src/client/client.ts`) — `BodhiPiClient` class  
Wraps `AgentSideConnection`. Methods like `kvGet(...)`, `kvSet(...)` marshal parameters and invoke `conn.callExtensionMethod(EXT_KV_GET, ...)`.

**Agent side** (`src/acp/agent.ts` `BodhiPiAcpAgent`) — implements ACP `Agent`  
On `handleExtensionMethod(method, params)`, dispatches to registered extension handlers:
- KV methods → `KvService`
- Session methods → `SessionGraphService`, `SessionInfoService`, session bootstrap
- Settings methods → `SettingsService`

## 3. KvStore Interface & Implementation

**`src/kv/kv-store.ts`** — Interface
```typescript
export interface KvStore {
  get(key: string): Promise<JsonValue | undefined>;
  set(key: string, value: JsonValue): Promise<void>;
  list(prefix?: string): Promise<Array<{ key: string; value: JsonValue }>>;
  remove(key: string): Promise<void>;
}

export const AUTH_PREFIX = "auth/";  // bodhi-pi reserves this prefix
```

**Namespacing convention:**
- `auth/<provider>` — provider credentials (API keys, base URLs)
- Other keys are user/extension-defined

**Secret masking** (`src/kv/kv-store.ts`):
```typescript
// Deep-copies value, replacing strings on { secret: true } nodes with "***"
export function maskSecrets(value: JsonValue): JsonValue { ... }

export function containsSecret(value: JsonValue): boolean { ... }
```

**Auth entry format** (`src/kv/auth-format.ts`):
```typescript
export interface ProviderAuth {
  api_key?: ProviderApiKey;       // { value: string, secret?: true }
  base_url?: string;
}

// Stored as: kv.set("auth/openai", normalizeProviderAuth({...}))
export function normalizeProviderAuth(config: ProviderAuth): JsonValue { ... }
export function parseProviderAuth(value: JsonValue | null): ProviderAuth | null { ... }
export function extractAuthApiKey(auth: JsonValue): string | undefined { ... }
export function extractAuthBaseUrl(auth: JsonValue): string | undefined { ... }
```

**`src/kv/kv-service.ts`** — Handler dispatcher
Implements `register(): Array<[string, ExtHandler]>` returning handlers for:
- `EXT_KV_SET` → `handleKvSet` (fires `auth_change` event if key starts with `AUTH_PREFIX`)
- `EXT_KV_GET` → `handleKvGet` (masks secrets in response)
- `EXT_KV_LIST` → `handleKvList` (masks all secrets)
- `EXT_KV_REMOVE` → `handleKvRemove` (fires `auth_change` event if key starts with `AUTH_PREFIX`)

**In-memory impl** (`src/kv/in-memory-kv-store.ts`):
```typescript
export function createInMemoryKvStore(): KvStore { ... }
```

**Reads from ACP are masked:** When an extension calls `_bodhi-pi/kv/get` or `_bodhi-pi/kv/list`, the service masks any value with `{ secret: true }` before returning. This prevents leaking credentials to the browser-side client.

## 4. Slash Commands (Client-Side Registry & Routing)

### Prompt Template Discovery

**`src/commands/prompt-templates.ts`** — Core types
```typescript
export interface PromptTemplate {
  name: string;
  description: string;
  argumentHint?: string;
  content: string;  // Template body with $1, $2, $@, $ARGUMENTS placeholders
  filePath: string;
}

// Substitutes $1/$2/… positional, $@ and $ARGUMENTS for all-joined, ${@:N:L} bash-style slicing
export function substituteArgs(content: string, args: string[]): string { ... }

// If text matches //<name>[ args…], expands the template; else returns text unchanged
export function expandPromptTemplate(text: string, templates: PromptTemplate[]): string { ... }
```

**`src/commands/discovery.ts`** — Filesystem walk
Loads `.bodhi-pi/commands/` from session cwd. Returns array of `PromptTemplate`.

### Slash Argument Parser

**`src/commands/slash-args.ts`** — Flat argument syntax (no popups)
```typescript
// Example: `/providers openai api_key="sk-1" base_url="https://..."`
export interface SlashArgs {
  positionals: string[];          // ["openai"]
  kwargs: Record<string, string>; // { api_key: "sk-1", base_url: "https://..." }
}

export function parseSlashArgs(input: string): SlashArgs { ... }
```

### Existing Built-In Slash Commands

From `bodhi-pi-cli/src/repl/commands.ts` (canonical reference):
- `/help` — show all commands
- `/new <optional-name>` — create a new session
- `/sessions` — list open sessions
- `/resume <session-id>` — resume a session
- `/model [<provider>/<model-id>]` — get/set the active model
- `/entries` — list session entries
- `/tree` — show session DAG
- `/navigate <entry-id>` — branch at an entry
- `/fork <entry-id>` — branch (edit message) at an entry
- `/clone <entry-id>` — clone the branch at an entry
- `/compact` — summarize and truncate history
- `/export` — serialize session to JSONL
- `/settings` — show active settings
- `/quit` — exit (CLI only)

### How a Slash is Routed

1. **Client input** → text like `/providers` or `/provider add ...`
2. **Client-side parse** → if first char is `/`, extract command name and args
3. **Client calls `BodhiPiClient.prompt(userText)`** → forwards full text (including `/`) to agent
4. **Agent side** (`src/acp/prompt-loop.ts`) → before dispatching to pi-agent-core:
   - Expands `/command-name arg1 arg2` using discovered templates
   - If no template found, passes text as-is to the LLM (LLM sees literal `/...`)
5. **Command registration via extension** (`ExtensionAPI.registerCommand`):
   - Extension provides `{ description, argumentHint, template }`
   - Runner adds it to the command array
   - Agent merges with project and builtin commands
   - Slash-command advertisement sent back via ACP `config_option_update` with `available_commands`

### How Notifications Render

**`src/acp/event-wiring.ts`** — Internal event handlers
When `auth_change`, `settings_change`, or `model_select` fires, automatically broadcasts `config_option_update` to refresh the client's model picker and command list.

**Client-side display** — Host-specific (CLI renders via chalk, web via React). bodhi-pi itself emits the events; hosts decide rendering.

## 5. Providers & Authentication

### Provider Data Model

**`src/kv/auth-format.ts`** — Provider config shape
```typescript
export interface ProviderAuth {
  api_key?: ProviderApiKey;     // { value: string, secret?: true }
  base_url?: string;
}

export interface ProviderAuthEntry {
  provider: string;
  config: ProviderAuth;
}
```

### Provider Storage & Lifecycle

**Storage:** KV store under `auth/<provider>` key  
**Format:** Normalized to `{ api_key: { value: "...", secret: true }, base_url: "..." }`

**Removal:** `_bodhi-pi/kv/remove` with key `auth/<provider>`

**Auth change events:** `src/kv/kv-service.ts` fires `auth_change` (action: "login" or "logout") whenever a key starting with `AUTH_PREFIX` is set or removed.

### Slash Commands for Providers

**From `bodhi-pi-cli/src/repl/commands.ts` (inferred pattern):**
- `/providers` — list configured providers (CLI shows from KV, web from model registry)
- `/provider add <name> [base_url=...] [api_key=...]` — add provider credentials to KV
- `/provider remove <name>` — remove provider from KV

### Model Registry

**`src/models/registry.ts`** — `ModelRegistry` class  
Aggregates models from:
1. Built-in pi-ai catalog (`getModels()`, `getProviders()`)
2. Host-supplied `models: Model<Api>[]`
3. Extension-registered providers (`ExtensionAPI.registerProvider(name, { model, getApiKey? })`)

On model select, registry:
- Resolves API key from KV (`auth/<provider>`), host `getApiKey`, then extension providers (in order)
- Builds `SessionConfigOption[]` advertised back to client
- Fires `model_select` event for internal wiring and extensions

- `e2e/helpers/in-memory/` — in-process ACP pair wiring

- `e2e/helpers/ws/` — WebSocket wiring

### Test Discipline

**Three parts:** setup (harness + seed), trigger (call ACP), assertion (check updates/filesystem/extension response).

**Flow consolidation:** When setup is identical and steps don't conflict, merge related tests + use `expect.soft(...)` per step.

**Timeout:** Global 30s (most tests must fit). Documented overrides to 60s for multi-prompt tests.

**Per-feature e2e model:** `gpt-4o-mini` (cheap, non-reasoning, deterministic). Cross-provider parity in `bodhi-pi/e2e/chat.e2e.ts`.

**Blackbox boundary:** `bodhi-pi/e2e/` drives test-apps via process spawn (`test-apps/*/dist/...`) or in-process harness. Never imports from test-app sources or sibling adapter packages (`@bodhiapp/bodhi-pi-*`). Required adapters inlined under `e2e/helpers/node-adapters/` (duplicated from upstream `bodhi-pi-node`, kept in sync).

## 8. CLAUDE.md Conventions

**Root `CLAUDE.md`** — Not found in this repo (no root CLAUDE.md).

**Per-package CLAUDE.md files:**

### bodhi-pi/CLAUDE.md
Key excerpts:

> **ACP is the public contract.** Drive via `AgentSideConnection` only. Internal `pi-agent-core` types and session-store impl types (`SessionEntry`, `SessionInfo`, `SessionRecord`) are not re-exported.

> **No silent defaults.** Missing required `BodhiPiConfig` field → factory throws. Mandatory: `models`, `defaultModelId`, `getApiKey`, `sessionStore`, `filesystem`.

> **Stable ACP over `unstable_*`.** Non-spec features use `_bodhi-pi/<area>/<verb>` extensions, advertised via `agentCapabilities._meta["bodhi-pi"]`.

> **Mirror coding-agent.** Read `packages/coding-agent/` first, strip TUI/Node parts, replicate field/method shape.

> **No fallbacks.** Throw at factory time if required field missing. `systemPrompt` is the sole exception.

> **pi-agent-core import policy:** `src/acp/agent.ts` imports `Agent` directly from `@earendil-works/pi-agent-core/dist/agent.js`, NOT the barrel, to avoid pulling Node-only transitive deps into browser runtimes.

### bodhi-pi-cli/CLAUDE.md
Key excerpts:

> **In-process ACP pair.** No real network transport — `repl/repl.ts` builds two `TransformStream`s and connects `AgentSideConnection` ↔ `ClientSideConnection` directly.

> **Slash-command set is canonical.** `src/repl/commands.ts` is the source of truth for `/help`, `/new`, `/sessions`, `/resume`, `/model`, `/quit`. `bodhi-pi-web/src/ui/commands.ts` is a port — keep them in sync.

> **`createCliAgent` is the test boundary.** All tests + e2e go through it. Never hand-build the same wiring elsewhere.

### bodhi-pi-http/CLAUDE.md
Key excerpts:

> **Each turn = one HTTP request.** `POST /acp` opens a long-lived SSE response. Agent is built fresh from persisted state, runs the turn, tears down.

> **Transparent `resumeSession` before `prompt`.** Handler invokes `agent.resumeSession({sessionId, cwd})` (hydrate without history replay) before `agent.prompt(...)`.

> **Cancel via in-memory `Map<sessionId, AbortController>`.** Process-local registry. Single-node by design.

## 9. Session Connection Lifecycle

### Where a Session Starts

**Agent side** (`src/acp/agent.ts` `BodhiPiAcpAgent`):

```typescript
// Request handler for ACP session/new
async handleNewSession(req: NewSessionRequest): Promise<NewSessionResponse> {
  const cwd = req.cwd || DEFAULT_CWD;
  const record = await this.sessionStore.create({ cwd, parentSessionId: ... });
  const sessionId = record.id;
  
  // Build session state
  const session = buildSessionStateFn({ ... }); // hydrate from record
  this.sessions.set(sessionId, session);
  
  // Fire session_start event
  await this.events.emit({
    type: "session_start",
    sessionId,
    cwd,
    reason: "new",
  });
  
  // Notify extensions
  await this.extensionRunner.notifySessionStart?.({ sessionId, session });
  
  return { sessionId, ... };
}
```

**On session connect / resume** (`src/sessions/session-bootstrap.ts`):

```typescript
// buildSessionState and rehydrateSession functions
export async function buildSessionState(...): Promise<SessionState> { ... }
export async function rehydrateSession(...): Promise<SessionState> { ... }
```

### Hydration Hook for MCPs

**`src/acp/agent.ts`** `BodhiPiAcpAgent` constructor and session handlers:

Currently, session bootstrap loads:
1. Session record from `SessionStore`
2. Settings (project + global + effective)
3. Models and API keys
4. Tools (builtin + extensions)
5. Commands (project + extension)

**Where MCPs would hook in:**
- **After step 2 (settings loaded):** Query KV for `mcp/<mcp-id>` entries; load MCP configs
- **In session bootstrap:** For each enabled MCP, discover tools and register them (similar to extension tools)
- **On `session_start` event:** Fire `mcp_hydrate` or `mcp_init` to allow MCPs to warm up caches or connections
- **On `session_shutdown` event:** Fire `mcp_teardown` to clean up resources

### Shared Transport Adapter

**Commit `f07087b7`** introduced:
- `LIFECYCLE_EVENT_METHOD` constant for emitting events to clients
- Shared SSE/HTTP transport utilities (likely in `src/wire/` or test-app HTTP layer)
- Reuse of browser-fs patterns (ZenFS) across runtimes

**Current event emission** (`src/acp/event-wiring.ts`):

```typescript
// Internal handler fired on auth_change, settings_change, model_select
const emitUpdate = async (sessionId: string) => {
  if (!sessions.has(sessionId)) return;
  const configOptions = await modelRegistry.buildAllConfigOptions(sessionId);
  await conn.sessionUpdate({
    sessionId,
    update: { sessionUpdate: "config_option_update", configOptions },
  });
};
```

For MCPs, a similar pattern would emit `available_tools_update` or `mcp_status_update` via `conn.sessionUpdate(...)`.

## Integration Points for MCPs

**Phase 1: Data Model & Storage**
1. Define `MCPServer` interface (id, url, auth, status)
2. Store via KV: `mcp/<mcp-id>` → serialized config
3. Use same masking pattern as provider auth (`{ secret: true }`)

**Phase 2: Lifecycle Hooks**
1. Add `session_mcp_discover` event (fired during session bootstrap)
2. Add `session_mcp_hydrate` event (after discovery, before first prompt)
3. Add `session_mcp_teardown` event (on session close)

**Phase 3: Tool Registration & Execution**
1. MCP discover tools → register via same `ExtensionAPI.registerTool` pattern
2. Tool execution: route `_bodhi-pi/mcp/execute-tool` to MCP HTTP client
3. Cache discovered tools in session state (keyed by MCP id)

**Phase 4: Client Surface**
1. `/mcp add <mcp-id> <url> [api_key=...]` — add to KV, fire hydration
2. `/mcp list` — show connected MCPs + discovered tools
3. `/mcp remove <mcp-id>` — remove from KV, cleanup

**Phase 5: Settings & Config**
1. Global/project settings layer for MCP defaults (auto-load on session start)
2. Per-session MCP enablement (settings scope)
