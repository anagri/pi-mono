# bodhi-pi e2e: sixth project `chrome-ext` — MV3 test-app + sandbox-port port

## Context

`packages/bodhi-pi/e2e/vitest.e2e.config.ts` runs the shared suite `e2e/shared/**/*.e2e.ts` against five projects today (`in-memory`, `cli`, `http`, `ws`, `browser`) — current baseline is **71 Test Files / 126 tests / 0 skipped** for `npm run test:e2e` (post-commit `20b14369`, the final `e2e-9` phase). This work adds a sixth project, `chrome-ext`, that runs the same shared suite a sixth time with the agent inside an unpacked MV3 extension's Web Worker, transport = Playwright driving a page served from `chrome-extension://<id>/index.html`.

The goal is one number: `cd packages/bodhi-pi && npm run test:e2e` reports six `Test Files` labels with zero skipped tests, and `just test` exits 0. The existing `bodhi-pi-chrome-ext` workspace continues to own its production UI + its own Playwright suite — both are out of scope. `test-app-chrome-ext` is a parallel, ACP-only artifact whose only job is to make `e2e/shared/*` runnable inside an MV3 extension.

## Locked decisions (from clarifying questions)

1. **Page reuse: one-time copy.** Files from `e2e/test-app-browser/src/frontend/` (App.tsx, main.tsx, worker.ts, index.html, lib/*) are copied verbatim into `e2e/test-app-chrome-ext/src/frontend/` once, then maintained separately. Easier than path aliases or build-time copy scripts; if test-app-browser drifts, manually re-sync.
2. **Build cadence: `test:e2e` npm script.** `packages/bodhi-pi/package.json#scripts.test:e2e` prepends `npm --workspace @bodhiapp/bodhi-pi-test-app-chrome-ext run build` so the dist is fresh before vitest spawns. Same pattern as test-app-browser today. Global-setup just loads.
3. **Persistent context: shared.** `launchPersistentContext` is called once in `e2e/global-setup.ts` with a fresh tmpdir as `userDataDir` and `--load-extension=<dist>` / `--headless=new`. Per-test isolation rides on the existing per-test random `userId` (already used by browser project) baked into Dexie dbName.
4. **Extension key: minted fresh.** Port `scripts/gen-ext-key.mjs` into `test-app-chrome-ext/scripts/`; run it once during scaffolding to mint a NEW RSA key + extension ID distinct from `bodhi-pi-chrome-ext`. Commit `manifest.json#key` and `.ext-id`; gitignore `key.pem`.

## Hard rules (carried)

- `bodhi-pi/e2e/**` (helpers AND `test-app-chrome-ext/`) imports only `@bodhiapp/bodhi-pi` (core SUT) and upstream `@earendil-works/*`. **No `@bodhiapp/bodhi-pi-*` sibling** (no `-node`, `-browser`, `-cli`, `-http`, `-chrome-ext`, `-ws-*`, `-web`). Sandbox machinery is ported in.
- 30s default `testTimeout`. No silent overrides. No skips. No emojis. Minimal comments.
- One commit per phase. Each commit body cites the gate it passed.
- DOM `data-testid` only in harness; no `page.evaluate` peek (the `afterEach` clean isn't needed because per-test `userId` already isolates Dexie).

## What gets built

### A. Port sandbox machinery into `e2e/helpers/browser-adapters/`

The current `browser-adapters/` skipped sandbox bits because `test-app-browser` runs with open CSP. Chrome MV3 enforces `extension_pages` CSP that forbids `'unsafe-eval'`, so AsyncFunction (used by `scripted-skill.e2e.ts` via `/skill:…` → `run_script`) must route through a sandbox iframe with its own relaxed CSP.

Verbatim ports from `packages/bodhi-pi-browser/src/` (with `// ported from packages/bodhi-pi-browser/src/<path>` header):

| New path | Source |
|---|---|
| `e2e/helpers/browser-adapters/sandbox/sandbox-bridge.ts` | `sandbox/sandbox-bridge.ts` |
| `e2e/helpers/browser-adapters/script-executor/sandboxed-browser-script-executor.ts` | `script-executor/sandboxed-browser-script-executor.ts` |
| `e2e/helpers/browser-adapters/extensions/sandboxed-browser-extension-loader.ts` | `extensions/sandboxed-browser-extension-loader.ts` |

Edits to existing files in `e2e/helpers/browser-adapters/`:

- `runtime/types.ts` — extend `InitMessage` with optional `sandboxPort?: MessagePort`.
- `runtime/bootstrap-worker.ts` — when `sandboxPort` is present in `InitMessage`, construct a `SandboxBridge` from it and substitute `createSandboxedBrowserScriptExecutor` + `createSandboxedBrowserExtensionLoader` in place of the direct variants. Without `sandboxPort`, behavior is identical to today (so test-app-browser is unaffected).

**Manifest contents** (template; key is minted fresh by `gen-ext-key.mjs`):

```json
{
  "manifest_version": 3,
  "name": "bodhi-pi test-app-chrome-ext (e2e)",
  "version": "0.0.0",
  "description": "ACP-only test app for bodhi-pi e2e shared suite under MV3",
  "key": "<minted>",
  "content_security_policy": {
    "extension_pages": "script-src 'self' 'wasm-unsafe-eval'; object-src 'self'",
    "sandbox": "sandbox allow-scripts allow-forms; script-src 'self' 'unsafe-eval' 'unsafe-inline' 'wasm-unsafe-eval' data:; script-src-elem 'self' 'unsafe-inline' data:; object-src 'self'"
  },
  "sandbox": { "pages": ["sandbox.html"] }
}
```

No `background` entry, no `action`, no `permissions`. Playwright navigates straight to `chrome-extension://<id>/index.html`.

**Vite config** mirrors `bodhi-pi-chrome-ext/vite.config.ts`: `base: "./"`, three rollup inputs (`index`, `sandbox`, and a noop placeholder dropped if we omit background), `worker.format: "es"`, `nodePolyfills` for both main + worker contexts, `node:crypto` alias → local `crypto-shim.ts`.

**App.tsx delta vs. test-app-browser**: at worker-spawn time, call `await createSandboxPort()` from `src/agent/sandbox.ts` and include `sandboxPort` in the `InitMessage` along with its MessagePort in the transfer list. Everything else (DOM contract, state machine, frame log, event log, seed parsing, ZenFS mount) is identical.

### C. New helper: `packages/bodhi-pi/e2e/helpers/chrome-ext-launch.ts`

- `ensureSharedChromeExtContext()` — singleton: reads `<test-app-chrome-ext>/.ext-id`, computes `distPath = <test-app-chrome-ext>/dist`, calls `chromium.launchPersistentContext(freshTmpdir, { headless: false, args: ["--disable-extensions-except=" + dist, "--load-extension=" + dist, "--headless=new", "--no-sandbox"] })`. Caches the context for the process lifetime.
- `closeSharedChromeExtContext()` — teardown counterpart; closes context, removes tmpdir.
- `launchChromeExtHarnessPage({userId, email, seed})` — `context.newPage()` + `page.goto("chrome-extension://<id>/index.html")` + fills setup form + clicks `setup-submit` + waits for `[data-test-state="ready"]`. Returns `{page, cleanup}` where cleanup closes the page (not the context).
